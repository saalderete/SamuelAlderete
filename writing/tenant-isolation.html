A test that reads every SQL query

November 2026 · 6 minute read · KasaPro

KasaPro is one deployment that serves several contractors and rental businesses. Every row of their data, from customers and estimates to invoices and signed agreements, belongs to exactly one business and carries that business's business_id. The whole security model comes down to one rule: every query that touches one of those rows filters on business_id.

If a single query forgets, one contractor sees another contractor's customers. That isn't a bug report you triage on Monday. It's the failure that ends the product, because the people using it are small businesses who handed me their customer list.

87 correct fences, and the 88th

For a long time the fence was written by hand at every call site:

SELECT * FROM invoices WHERE id = ? AND business_id = ?

When I counted, there were 87 of them, and every one was correct. That was the problem. The next one would also be written by hand, and the day someone types the id check and forgets the business_id check, nothing fails. The page renders and the data is simply someone else's.

So the first change was to make the safe query the easy one. findOwned(table, id, businessId) fetches a row only if it belongs to the caller:

async function findOwned(table, id, businessId, options = {}) {
  if (!OWNED_TABLES.has(table)) {
    throw new Error(`findOwned: "${table}" is not an allowlisted tenant table`);
  }
  const columns = options.columns || "*";
  const [rows] = await db.query(
    `SELECT ${columns} FROM ${table} WHERE id = ? AND business_id = ?`,
    [id, businessId]
  );
  return rows[0] || null;
}

Two details matter here. A table name can't be a bind parameter, because SQL placeholders hold values, not identifiers, so the name is checked against a fixed allowlist instead of being spliced in on faith. And the function returns null for both "doesn't exist" and "exists but belongs to someone else." If those gave different answers, a 404 that only appears for rows you don't own would tell an attacker which IDs are real.

An audit proves the code was right the day it was read

A helper only protects the code that uses it. What I wanted was a guarantee about code that doesn't exist yet. The answer was a test, lib/tenancy.test.js, that reads every JavaScript file under routes/, lib/ and scripts/, pulls out every SQL statement, and fails the build if any statement touching a tenant table doesn't mention business_id.

It doesn't parse JavaScript. It looks for the SQL verbs, then reads forward to the end of the enclosing db.query(...) call:

const re = /(SELECT|INSERT\s+INTO|UPDATE|DELETE\s+FROM)\b/gi;
while ((m = re.exec(source)) !== null) {
  const chunk = source.slice(m.index, m.index + 1400);
  const end = chunk.indexOf(");");
  out.push({ sql: end > 0 ? chunk.slice(0, end) : chunk, line: ... });
}

The first version stopped at the end of the string literal instead, and it reported correct queries as unscoped, because a multi-line statement often carries its AND business_id = ? several lines down. Reading to the closing ); includes the parameter array too, which is harmless: it holds the variable businessId, not the column name.

When something fails, the message says why it matters and what to do. Here it is for a made-up bad query:

Queries on tenant-owned tables with no business_id filter.
Each one can return another contractor's data. Add the filter, or if it is
genuinely global, add it to ALLOWLIST in this file with a reason.

routes/example.js:42  [invoices]
      SELECT total FROM invoices WHERE id = ?

The allowlist has to explain itself

Some queries really can't be scoped to a business, and pretending otherwise just teaches people to work around the test. So there is an allowlist, and every entry carries a reason written for the next person who reads it. Three examples:

  • Signup. Checking whether an email is taken has to look across every business, because emails are unique across the whole system. It returns existence only, never another tenant's row.
  • Signing links. A customer signing an estimate has no session. The 256-bit token in the link is the authorization, and it's looked up before anything is shown or written.
  • Square webhooks. Square knows an order ID, not a KasaPro business. KasaPro minted that order ID for one specific invoice or rental, so it identifies the tenant rather than needing to be filtered by one.

Adding a line to that list should feel deliberate, because it's the only way past the check.

What it doesn't prove

It's a text match, not a proof. A query that mentions business_id in the wrong place would pass. Three tables (estimate_items, job_notes, job_photos) have no business_id of their own; they're safe only because the handler has already loaded the parent job or estimate with a business filter. I checked those paths by hand, and a second, coarser test fails if one of those tables shows up in a file that never mentions business_id at all.

The same file holds two other rules I learned to write down:

  • Public tokens are at least 128 bits. Signing and payment links carry no session, so a short token is the classic way a multi-tenant app leaks across tenants. The test fails on any randomBytes(n) with n under 16.
  • Uploads live outside public/. Job photos often show the inside of someone's home. If the upload folder sits under the static directory, anyone who guesses a filename can see every tenant's photos. That rule exists because it happened once.

A code review protects the code you reviewed. A test protects the next query too.

KasaPro has 940 automated tests now, and this is the file I'd keep if I could keep only one. The whole file runs in about 140 milliseconds, and it turns "be careful with tenant data" from something I have to remember into something the build checks.
